     1→# Hardening Roadmap — Defense-in-Depth Against 30 Attack Vectors
     2→
     3→This document maps the operator's "blindagem" mandate (30 attack vectors) to
     4→a phased hardening plan. It is the structural counterpart to `SECURITY.md`:
     5→where `SECURITY.md` inventories regression tests that pin already-fixed
     6→properties, this document inventories attack vectors that are not yet
     7→defended and proposes how to close each gap.
     8→
     9→The discipline is the same one this thread consolidated:
    10→
    11→1. **Diagnose before fixing** — for each gap, demonstrate the failure mode
    12→   empirically (a test that fails against the current code) before
    13→   implementing the defense.
    14→2. **Structural tests as acceptance criteria** — not best-effort. Each
    15→   hardening phase has explicit test assertions that must pass before the
    16→   phase is marked complete.
    17→3. **`SECURITY.md` for regressions** — once a defense lands, add a REG-NNN
    18→   entry so a future maintainer cannot "simplify" it back into the
    19→   vulnerable shape.
    20→4. **Real-mechanism tests** — live process, real socket, real RPC, not
    21→   pure-function simulations of the defense logic.
    22→
    23→### Permanent principle — adversarial cryptographic tests
    24→
    25→> **Every new cryptographic implementation must ship with at least one
    26→> test that explicitly attempts to break the promised security property.**
    27→
    28→This principle was added after H0.3 (audit log hash-chain) revealed that
    29→`JSON.stringify(entry, sortedKeysArray)` (the replacer-array form) was
    30→silently dropping nested keys inside `payload` from the hash. An attacker
    31→could modify the payload without breaking the chain. The bug was caught
    32→only by the tamper-detection test — not by code inspection, not by the
    33→happy-path tests, not by the chain-linkage tests. Only by the test that
    34→**deliberately tried to break the property the hash chain was supposed to
    35→guarantee**.
    36→
    37→The pattern is now mandatory for every cryptographic primitive. Examples:
    38→
    39→| Primitive | Adversarial test must demonstrate |
    40→|---|---|
    41→| hash-chain | tampering with a record's payload (including nested fields) breaks verification; deleting a record breaks verification; reordering records breaks verification |
    42→| KDF / encryption | a legacy blob (without version fields) still decrypts only with the correct passphrase; a blob with a manipulated ciphertext fails to decrypt; a blob with a wrong auth tag is rejected |
    43→| key rotation | rotation with the wrong old passphrase fails for ALL blobs (no partial rotation); rotated blobs decrypt with the new passphrase and NOT with the old one; idempotency holds |
    44→| signature | modifying any byte of the signed payload invalidates the signature; signing under a different domain separator does not verify under the expected domain |
    45→| audit log | insertion of a forged entry at any position is detected; removal of the genesis entry is detected; replay of an old entry under a new seq is detected |
    46→| transaction simulation | a simulated revert blocks broadcast; a simulated state diff that diverges from the expected diff blocks broadcast |
    47→| approval cap | an unlimited approval (`type(uint256).max`) is rejected; an approval that exceeds the configured cap is rejected; an approval that exceeds the on-chain balance is rejected |
    48→| RPC quorum | a malicious endpoint returning a wrong chain id, a stale block number, or a wrong balance is detected and quarantined; quorum disagreement blocks the action |
    49→
    50→A cryptographic primitive that ships without an adversarial test is
    51→**incomplete by definition** — it has not been proven to actually defend
    52→the property it claims to defend. The hash-chain bug is the canonical
    53→example: the code looked correct, the happy-path tests passed, the
    54→structural tests passed, and the chain was still security theater until
    55→the adversarial test was written.
    56→
    57→## Scope — what the app can and cannot defend against
    58→
    59→The 30 vectors span three concentric perimeters. The app code can only
    60→defend the innermost two; the outermost requires operational policy,
    61→endpoint hardening, and human controls that no amount of app code can
    62→replace. Conflating the three leads to security theater — defenses that
    63→look like they cover the vector but don't, because the vector operates
    64→outside the app's perimeter.
    65→
    66→| Perimeter | What lives here | Defense mechanism | In scope for app code? |
    67→|---|---|---|---|
    68→| **App-internal** | Trade execution, signing, RPC dispatch, contract interaction, portfolio math | Code + tests + regression inventory | **Yes** — fully in scope |
    69→| **App-edge** | HTTP responses, browser embedding, RPC endpoints the app talks to | Headers, CSP, RPC failover, address book | **Yes** — partially in scope |
    70→| **Operational / endpoint** | Operator's machine, CI/CD pipeline, human workflows, contractor access | Policy, hardware keys, procedures, endpoint hardening | **No** — app can SUPPORT (audit logs, address book UI) but cannot DEFEND |
    71→
    72→The third perimeter is explicitly out of scope for code, but each vector
    73→in it lists what the app CAN do to support the operational defense. This
    74→is not a dodge — it is a precise boundary. Pretending the app can defend
    75→against deepfakes or clipboard hijackers would be the exact pattern this
    76→thread has rejected: "documenting the intention is not the same as
    77→proving the code respects the intention." The app cannot prove anything
    78→about the operator's clipboard; only the endpoint can.

    82→## Threat Model — 30 Vectors in 8 Layers
    83→
    84→### Layer 0: Foundational — key management & crypto (IN FLIGHT via Phase 1)
    85→
    86→| Vector | Existing mitigation | Gap | Defense |
    87→|---|---|---|---|
    88→| **Comprometimento de Chaves Operacionais** | Signer isolation (Phase 1: M1 done, M2.x in progress) — keys live in a separate process, not in the Next.js process | M2.3+ not yet complete; keys still touched by in-process `WalletVault` until M2.3 moves it | Complete M2.3 (move `WalletVault` to signer process) + M3 (sign RPC) + M4 (writer lease) |
    89→| **Gestão de Chaves em Hot Wallets** | 50/50 cold reserve split (profit → 50% USDC cold reserve, 50% reinvested); signer isolation limits hot-key exposure to the signer process | Cold reserve is a DB row, not an actual cold wallet; no HSM integration | H0-future: actual cold-storage workflow (manual withdrawal to hardware wallet); document that "cold reserve" = "not auto-traded", not "air-gapped" |
    90→| **Erros de Implementação Criptográfica** | Uses `ethers` v6 (audited lib); no custom crypto; AES-GCM via Node `crypto` for vault encryption | Constant-time comparison not used for passphrase verification; key zeroization incomplete until M2.3 | M2.3 adds zeroize-on-disconnect; H7 adds property tests for crypto paths |
    91→
    92→### Layer 1: MEV / On-chain adversarial (GAP — no defense exists)
    93→
    94→| Vector | Existing mitigation | Gap | Defense |
    95→|---|---|---|---|
    96→| **Front-Running Bots** | None — slippage hardcoded at 30bps in paper-trader.ts for paper mode; live DEX path has no MEV protection | No private mempool, no commit-reveal, no slippage tolerance configuration | H1: integrate Flashbots Protect (or chain-equivalent: Merlin for Base, MEV-Share); configurable slippage; order splitting |
    97→| **Sandwich Bots** | None — same gap as front-running | No private mempool, no mempool privacy | H1: private mempool submission (same as front-running); sandwich-resistant routing (split across blocks); slippage tight enough to make sandwich unprofitable |
    98→| **Sniper Bots** | None — the bot IS a sniper-style scanner (rising-tokens.ts), but has no defense AGAINST being sniped by faster bots when it buys | No priority fee strategy, no private mempool | H1: private mempool for entries; configurable priority fee; "wait N blocks" confirmation before treating a new token as tradeable |
    99→| **Arbitrage Bots** | None — the bot's own exits (TP/SL) are visible on-chain if using limit orders; marketable limit orders can be front-run by arb bots | No defense against arb bots extracting value from the bot's own predictable exits | H1: randomize exit timing (jitter); use TWAP for exits; avoid predictable TP/SL that arb bots can target |
   100→
   101→**H1 acceptance criteria (structural):**
   102→- A test that simulates a sandwich attack (buy → victim buy → sell) against
   103→  the bot's order flow, and asserts the bot's order was submitted via the
   104→  private mempool path (not the public mempool), OR the slippage tolerance
   105→  rejected the sandwiched execution.
   106→- A test that asserts slippage tolerance is configurable and enforced (a
   107→  fill beyond tolerance is reverted, not silently accepted).
   108→- A test that asserts exit timing has jitter (not deterministic), so arb
   109→  bots cannot predictably target the bot's exits.
   110→
   111→### Layer 2: Token / Contract fraud (PARTIAL — scam-detector covers some)
   112→
   113→| Vector | Existing mitigation | Gap | Defense |
   114→|---|---|---|---|
   115→| **Honeypot** | scam-detector sub-scorer (turnover + liquidity check) — scores 0-100, blocks below threshold | Only checks buy-side liquidity; doesn't simulate sell (the actual honeypot test) | H2: integrate GoPlus/honeypot-is API for sell-simulation; extend scam-detector with a "can actually sell" sub-scorer |
   116→| **Rug Pull** | scam-detector sub-scorers (liquidity lock via DexScreener, holder concentration, dev wallet %) | Doesn't verify mint authority, doesn't check if LP is actually locked (only DexScreener's reported lock) | H2: on-chain LP lock verification (call the lock contract); mint authority check; transfer-owner check |
   117→| **Smart Contract Exploits** | scam-detector contract sub-scorer (verified source, mint function, owner privileges) | No pre-trade simulation; no function-selector allowlist for the swap router | H2: pre-trade simulation via fork (tenderly or local fork); allowlist of permitted router function selectors; reject unknown selectors |
   118→| **Unlimited Approval Drain** | None — no approval management code exists (paper mode only currently) | When live DEX trading lands, the default ERC-20 `approve(max)` pattern is a known drain vector | H2: exact-amount approvals (approve only the swap amount); auto-revoke after swap completes; approval tracking + expiry |
   119→| **Liquidity Mining Frauds** | None — no staking/farming code exists | If staking is ever added, reward-token legitimacy + staking contract audit needed | H2-future: if staking is added, require staking contract audit + reward token legitimacy (is the reward token itself a scam?) |
   120→| **Ataques de "First Depositor"** | None — no vault share code exists | If the bot ever deposits into yield vaults, first-depositor inflation attack applies | H2-future: if vault deposits are added, check vault share/totalSupply ratio; prefer vaults with virtual shares (ERC-4626 with dead shares) |
   121→
   122→**H2 acceptance criteria:**
   123→- A test that asserts approvals are exact-amount (not `type(uint256).max`),
   124→  with an auto-revoke confirmation after the swap.
   125→- A test that asserts a known-honeypot token (synthetic fixture: a contract
   126→  that buys succeed but sells revert) is rejected by the extended
   127→  scam-detector before the order is placed.
   128→- A test that asserts pre-trade simulation rejects orders that would revert
   129→  on-chain (catches logic errors + reentrancy traps before they cost gas).
   130→
   131→### Layer 3: Signature / Approval hygiene (GAP — no signing UX exists yet)
   132→
   133→| Vector | Existing mitigation | Gap | Defense |
   134→|---|---|---|---|
   135→| **Signature Phishing** | None — no signing UX exists (signer isolation handles the signing, but the operator approves what to sign via the dashboard) | When the operator approves a sign request, a phishing payload (e.g., `permit` signature that grants unlimited allowance) looks identical to a legitimate swap | H3: EIP-712 typed-data display (human-readable signing payloads); reject raw `personal_sign` / `eth_sign`; domain separation; warning on `permit`-shaped payloads |
   136→| **Revogação Inconsistente de Permissões** | None — no approval tracking | Approvals granted and forgotten are a persistent drain vector | H3: approval registry (DB table tracking every active approval); auto-revoke cron; dashboard view of open approvals |
   137→
   138→**H3 acceptance criteria:**
   139→- A test that asserts the signing path rejects `personal_sign` and
   140→  `eth_sign` (only EIP-712 typed data is permitted).
   141→- A test that asserts a `permit`-shaped payload triggers an explicit
   142→  warning in the approval UI (not a silent accept).
   143→- A test that asserts the approval registry tracks every approval and the
   144→  auto-revoke cron revokes expired ones.
   145→
   146→### Layer 4: Infrastructure (GAP — single RPC, no oracle aggregation)
   147→
   148→| Vector | Existing mitigation | Gap | Defense |
   149→|---|---|---|---|
   150→| **Dependência de RPC Centralizados** | None — single RPC endpoint per chain (configured in config.ts) | Single RPC = single point of failure + single point of censorship | H4: multi-RPC failover (primary + secondary + tertiary); health-checked; automatic failover; RPC diversity score (different providers, not just different endpoints of same provider) |
   151→| **Manipulação de Oráculos** | None — uses DexScreener spot price (already a form of spot oracle, not TWAP) | Spot price is manipulable via flash loans; no deviation check between sources | H4: TWAP for price decisions (not spot); multi-source aggregation (DexScreener + on-chain pool + CEX price for cross-listed); circuit breaker on deviation > X% |
   152→| **Comprometimento de CI/CD** | Partial — pre-push hook runs `test:ci` (REG-004); branch protection status unknown | No signed commits; no SLSA provenance; no reproducible build verification | H4: GPG/Sigstore-signed commits; SLSA Level 2+ provenance; reproducible build check in CI |
   153→| **Supply Chain Attacks** | Partial — `package-lock.json` exists; npm audit possible | No dependency pinning enforcement; no SBOM; no integrity check on postinstall scripts (ironic, given the hook itself runs on postinstall) | H4: `npm ci` enforcement (no `npm install` in CI); pinned dependencies with integrity hashes; SBOM generation; `npm audit` as gate |
   154→
   155→**H4 acceptance criteria:**
   156→- A test that asserts RPC failover works: when the primary RPC is
   157→  unreachable, the secondary is used within N seconds, with a logged notice.
   158→- A test that asserts a price deviation > X% between sources triggers the
   159→  circuit breaker (trade is not placed).
   160→- A test that asserts `npm ci` (not `npm install`) is the install command
   161→  in CI, and that the lockfile integrity is verified.
   162→
   163→### Layer 5: Privacy / Browser (GAP — no CSP, no frame protection)
   164→
   165→| Vector | Existing mitigation | Gap | Defense |
   166→|---|---|---|---|
   167→| **Vazamento de Privacidade via RPC** | Partial — per-IP rate limiting (REG-002) limits abuse, but RPC payloads themselves can leak the operator's positions/strategy to the RPC provider | RPC provider sees every call (balances, pending txs) | H5: prefer private RPCs (Infura with privacy, Alchemy with privacy); batch requests to reduce signal; avoid polling patterns that reveal strategy |
   168→| **Injeção de Provider em Iframes** | None — no CSP, no X-Frame-Options, no frame-ancestors | Dashboard can be iframed by a malicious page, which can then postMessage-inject a fake provider | H5: `X-Frame-Options: DENY` + `Content-Security-Policy: frame-ancestors 'none'` in Next.js middleware; reject `window.opener` access; `Cross-Origin-Opener-Policy: same-origin` |
   169→
   170→**H5 acceptance criteria:**
   171→- A test that asserts the dashboard response includes `X-Frame-Options: DENY`
   172→  and `Content-Security-Policy: frame-ancestors 'none'` headers.
   173→- A test that asserts a cross-origin `window.open` to the dashboard cannot
   174→  access `window.opener` (COOP header present).
   175→
   176→### Layer 6: Address hygiene (GAP — no address book)
   177→
   178→| Vector | Existing mitigation | Gap | Defense |
   179→|---|---|---|---|
   180→| **Address Poisoning** | None — no address book; operator types/pastes addresses | Attacker sends a dust transaction from an address that looks similar to a known counterparty; operator later pastes the wrong address from transaction history | H6: address book with verified entries (checksummed, ENS-resolved, manually confirmed); new-address warning (any send to an address not in the book requires explicit confirmation); clipboard re-display (pasted addresses are re-shown for confirmation before submission) |
   181→
   182→**H6 acceptance criteria:**
   183→- A test that asserts a send to an address NOT in the address book triggers
   184→  the new-address confirmation flow (not a silent send).
   185→- A test that asserts a pasted address is re-displayed for confirmation
   186→  (not submitted directly from clipboard).
   187→
   188→### Layer 7: Logic correctness (PARTIAL — risk-manager limits blast radius)
   189→
   190→| Vector | Existing mitigation | Gap | Defense |
   191→|---|---|---|---|
   192→| **Reentrância** | N/A — the bot doesn't deploy its own contracts; reentrancy is a concern for the contracts it INTERACTS with | No reentrancy check on the swap router side (but this is the router's problem, not ours) | H7: pre-trade simulation (H2) catches reentrancy traps; no custom contracts to protect |
   193→| **Erros de Lógica** | Risk-manager (5 circuit breakers limit blast radius); test-vault.ts (20 scenarios) | No property tests / invariant tests for portfolio math (profit split, reserve cut, drawdown calc) | H7: property-based tests for portfolio math (fast-check); invariant tests (e.g., "sum of all positions + balance + reserve = initialCapital + realizedPnl" must always hold) |
   194→
   195→**H7 acceptance criteria:**
   196→- A property test that runs 1000 randomized trade sequences and asserts
   197→  the portfolio invariant (sum of positions + balance + reserve = initial +
   198→  realizedPnl) holds after every operation.
   199→- A property test that asserts the 50/50 split is exact (no rounding loss).
   200→
   201→### Layer 8: Operational / endpoint (OUT OF SCOPE for app code)
   202→
   203→These vectors operate outside the app's perimeter. The app cannot defend
   204→against them — only the operator's endpoint, CI/CD pipeline, and human
   205→workflows can. Listing them here to be explicit about the boundary.
   206→
   207→| Vector | Why it's out of scope | What the app CAN do to support |
   208→|---|---|---|
   209→| **Fake Support** | Attacker impersonates support via email/Discord/Telegram. The app cannot verify who is messaging the operator. | Dashboard prominently displays the official support channel; "verify you are talking to us" notice |
   210→| **Airdrop Scams** | Attacker sends fake airdrop; operator connects wallet to claim; wallet drained. The app doesn't claim airdrops. | Airdrop-claim is not a feature; if ever added, require address allowlist + contract audit |
   211→| **Clipboard Hijackers** | Malware on operator's machine replaces copied addresses. The app cannot see the clipboard before paste. | H6 clipboard re-display (pasted addresses re-shown for confirmation) catches this AT THE APP BOUNDARY — the malware replaced the clipboard, but the app shows the operator what was actually pasted before submitting |
   212→| **Infostealers** | Malware steals cookies, session tokens, wallet files from the operator's machine. The app cannot detect malware. | Short session TTL; re-auth for sensitive actions; hardware key support (FIDO2) for dashboard auth |
   213→| **Deepfakes e Áudio Sintético** | Attacker uses deepfake audio/video to impersonate the operator or a colleague, authorizing a transfer. The app cannot verify the identity of someone speaking. | Out of scope. Operational policy: no authorization via voice/video; all authorizations go through the dashboard with MFA |
   214→| **Phishing Hiper-personalizado** | Attacker uses OSINT to craft a targeted phishing message. The app cannot filter the operator's inbox. | Out of scope. Operational policy: security awareness training; hardware keys; dashboard MFA |
   215→| **Ameaças Internas e Contratados** | A contractor with legitimate access goes rogue. The app cannot detect intent. | Audit logs (every action logged with actor + timestamp); least-privilege roles; access revocation workflow; offboarding checklist |
   216→
   217→**The boundary is load-bearing.** If a future maintainer tries to "defend
   218→against deepfakes" inside the app code, they will produce security theater
   219→— code that looks defensive but cannot actually detect a deepfake. The
   220→honest answer is operational policy + hardware keys + MFA, none of which
   221→live in this repo. The app's job is to SUPPORT those controls (audit logs,
   222→MFA, short sessions) not to REPLACE them.

   226→## Phased Roadmap
   227→
   228→### H0: Complete foundational (parallel to M2.3, M3, M4) — ✓ COMPLETE
   229→- Finish signer isolation: M2.3 (move WalletVault) → M3 (sign RPC) → M4 (writer lease)
   230→- This fully closes Layer 0 (Operational Key Compromise, Hot Wallet Key Management, Cryptographic Implementation Errors via zeroize-on-disconnect)
   231→- **No new hardening work starts until H0 is done** — Layer 0 is the foundation that H1-H7 build on. Building MEV defenses on top of a non-isolated signer would be rework.
   232→- **STATUS**: H0.1 (KDF + derivation parameters audit), H0.2 (secret storage audit), H0.3 (audit log hash-chain), H0.4 (key rotation / versioning), H0.5 (cryptographic guarantees review) — all complete. CI gate: 9 files / 78 checks. Critical hash-chain bug (JSON.stringify replacer-array dropping payload keys) caught + fixed during H0.3 testing. docs/CRYPTO.md and SECURITY.md H0 section written.
   233→
   234→### H1: Transaction lifecycle hardening (Layers 1+2+4) — ✓ COMPLETE
   235→After H0 closed the foundational crypto base, H1 hardens the entire
   236→transaction lifecycle: from RPC fan-out, through pre-broadcast
   237→simulation, to approval hygiene and MEV baseline. H1 deliberately
   238→collapses what the original roadmap had as separate H1 (MEV), H2
   239→(simulation + approvals), and H4 (RPC failover) into a single
   240→hardening pass — the rationale is to keep the entire on-chain
   241→communication + execution layer hardened as one perimeter before any
   242→new signer feature (M3/M4) lands on top of it.
   243→
   244→**STATUS** (Jul 15 2026): all four subphases complete.
   245→- H1.1 RPC Resilience — `src/lib/chain/rpc-resilience.ts` —
   246→  `QuorumRpcClient` with quorum, health score, failover, circuit
   247→  breaker. 46 assertions across 16 scenarios. Bug caught: double-
   248→  counting in `recordFailure`.
   249→- H1.2 Transaction Simulation — `src/lib/chain/simulation-gate.ts` —
   250→  `SimulationGate` with revert detection, state-diff comparison,
   251→  tolerance-bounded amount checks, gas cap. 46 assertions across 14
   252→  scenarios.
   253→- H1.3 Approval Hardening — `src/lib/chain/approval-hardening.ts` —
   254→  `ApprovalGate` with cap enforcement, unlimited-approval hard block,
   255→  over-approval block, ledger + revocation. 36 assertions across 15
   256→  scenarios. Bug caught: cap-vs-overapproval ordering.
   257→- H1.4 MEV Baseline — `src/lib/chain/mev-baseline.ts` —
   258→  `computeSlippageLimit`, `checkSlippage`, `detectSandwich`,
   259→  `Relay` interface + `PublicMempoolRelay` + `PrivateRelayStub`.
   260→  47 assertions across 16 scenarios.
   261→
   262→CI gate: **13 files / 253 checks** (was 9 files / 78 checks at H0 close).
   263→Each subphase ships with adversarial tests per the permanent principle.
   264→The hardened primitives are NOT yet wired into any production code path
   265→— they wait for M3 to consume them, ensuring the live-trading path is
   266→born hardened rather than retrofitted.
   267→
   268→H1 subphases (per operator mandate):
   269→- **H1.1 — RPC Resilience**: multi-RPC with quorum; per-endpoint health
   270→  score; automatic failover; per-RPC circuit breaker.
   271→- **H1.2 — Transaction Simulation**: mandatory simulation before any
   272→  broadcast; comparison between expected and simulated state diff;
   273→  automatic block on divergence.
   274→- **H1.3 — Approval Hardening**: approval inventory; maximum approval
   275→  cap; automatic revocation when possible; hard block on unlimited
   276→  approvals (`type(uint256).max`).
   277→- **H1.4 — MEV Baseline**: abnormal slippage detection; dynamic
   278→  slippage limit; sandwich detection via simulation; abstraction
   279→  prepared for private relays (Flashbots / Merlin / MEV-Share) WITHOUT
   280→  depending on them yet.
   281→
   282→Acceptance criteria (structural + adversarial, per the permanent
   283→principle above):
   284→- RPC quorum test: a malicious endpoint returning wrong chain id /
   285→  stale block / wrong balance is detected and quarantined; quorum
   286→  disagreement blocks the action.
   287→- Simulation test: a simulated revert blocks broadcast; a state-diff
   288→  divergence blocks broadcast.
   289→- Approval test: an unlimited approval is rejected; an approval
   290→  exceeding the cap is rejected; an approval exceeding the on-chain
   291→  balance is rejected.
   292→- MEV test: a sandwich pattern (front-run + back-run around the
   293→  victim tx) is detected from simulation; abnormal slippage blocks
   294→  broadcast.
   295→- Each subphase ships with at least one adversarial test per the
   296→  permanent principle.

   346→3. **H2** — Contract interaction hardening (on-chain LP lock verification, mint authority, extended scam-detector).
   347→4. **M3** — Sign RPC (now lands on a hardened base).
   348→5. **M4** — Writer lease.
   349→6. **H3-H8** — Subsequent hardening phases (signature hygiene, infra, privacy, address hygiene, logic, operational support).

   391→## Extended Threat Model — List 2 (traditional cybersecurity + AI vectors)
   392→
   393→The operator issued a second mandate with ~46 additional vectors. After
   394→deduplication (several items were listed 2-3 times within the list) and
   395→cross-referencing against List 1 (Supply Chain, Falhas Criptográficas,
   396→Deepfakes, Pipeline de Build, Recrutamento de Insider already appear in
   397→Layers 4, 0, 8 above), ~30 genuinely new vectors remain. They fall into
   398→6 new layers:
   399→
   400→### Layer 9: Web application security (OWASP Top 10:2025) — IN SCOPE
   401→
   402→| Vector | Existing mitigation | Gap | Defense |
   403→|---|---|---|---|
   404→| **Broken Access Control** | NextAuth session check on API routes (partial) | No RBAC; no object-level authorization (IDOR); admin vs operator not distinguished | H9: RBAC (admin / operator / viewer roles); object-level authz on every DB query (not just route-level); deny by default |
   405→| **SQL Injection** | Prisma parameterized queries (mitigates by construction) | Raw queries if any exist need audit; no SQL injection in Prisma path | H9: audit for `$queryRaw` / `$executeRaw` usage; ban raw SQL unless reviewed; structural test that asserts parameterization |
   406→| **XSS** | React auto-escaping in JSX (mitigates by construction) | `dangerouslySetInnerHTML` if used anywhere; user-generated content (scam reports, log messages) rendered unsafely | H9: audit for `dangerouslySetInnerHTML`; CSP with `script-src 'self' 'nonce-...'`; sanitize user content before storage |
   407→| **Security Misconfiguration** | Partial — `.env` for secrets, `NODE_ENV` check | No security headers audit; no CORS policy; default credentials check; debug mode in prod | H9: Next.js middleware for security headers (HSTS, X-Content-Type-Options, Referrer-Policy); CORS allowlist; production config audit |
   408→| **OWASP Top 10:2025 (broad)** | (encompasses all above + below) | No systematic OWASP compliance review | H9: run OWASP ZAP / Burp scan against the dashboard; remediate findings |
   409→
   410→**H9 acceptance criteria:**
   411→- A test that asserts every API route checks authorization (not just authentication) — no IDOR (object-level access control).
   412→- A test that asserts no `$queryRaw` / `$executeRaw` exists without parameterization (grep-based gate).
   413→- A test that asserts security headers are present on every response (HSTS, X-Content-Type-Options, CSP, Referrer-Policy).
   414→- A test that asserts `dangerouslySetInnerHTML` is not used without explicit sanitization.
   415→
   416→### Layer 10: Identity & Account security — IN SCOPE (dashboard auth)
   417→
   418→| Vector | Existing mitigation | Gap | Defense |
   419→|---|---|---|---|
   420→| **Identity Takeover / ATO** | NextAuth with credentials provider | No MFA; no session device binding; no anomaly detection on login | H10: MFA (TOTP or FIDO2); session device fingerprinting; login anomaly alerts (new geo, new device, impossible travel) |
   421→| **Credential Stuffing** | NextAuth rate limiting (if configured) | No breach-password check (HIBP API); no lockout after N failures | H10: rate limit login per IP + per account; lockout after 5 failures; HIBP API check on password set/change |
   422→| **Identidade Digital Falsa / Identidades Sintéticas** | None | No identity verification for dashboard access (single-operator assumption) | H10: if multi-operator ever added, require identity proofing; for single-operator, document the assumption + enforce hardware key |
   423→
   424→**H10 acceptance criteria:**
   425→- A test that asserts login rate limiting works (N failures → lockout).
   426→- A test that asserts MFA is enforced (no session without second factor).
   427→- A test that asserts session device fingerprinting rejects a session from a new device without re-auth.
   428→
   429→### Layer 11: Availability / DDoS — PARTIALLY IN SCOPE
   430→
   431→| Vector | Existing mitigation | Gap | Defense |
   432→|---|---|---|---|
   433→| **DDoS volumétrico** | None (single host, Caddy reverse proxy) | No CDN/WAF in front; single host = single point of failure | Out of scope for app code. Infra: CDN (Cloudflare) in front, geographic rate limiting. App-side: graceful degradation under load (shed non-critical requests) |
   434→| **DDoS de aplicação** | Per-IP rate limiting (REG-002) on vault endpoints | No rate limiting on other API routes; no request complexity budget | H11: rate limit ALL API routes (not just vault); request complexity budget; slow-loris protection (request timeout) |
   435→| **Monocultura da Internet** | Next.js + Node (common stack) | Dependency monoculture (all Node) is an industry-level concern, not app-level | Out of scope. Operational: diversify critical infra across providers |
   436→
   437→**H11 acceptance criteria (app-side only):**
   438→- A test that asserts every API route has a rate limit configured.
   439→- A test that asserts request timeout is enforced (no slow-loris hang).
   440→- A test that asserts the app degrades gracefully under load (returns 503, not crash).
   441→
   442→### Layer 12: Ransomware & Extortion — OUT OF SCOPE (endpoint/operational)
   443→
   444→| Vector | Why out of scope | App-side support |
   445→|---|---|---|
   446→| **Ransomware e Extorsão Digital** | Endpoint threat; app cannot detect or prevent ransomware | Backups (DB export exists in system/backup route); immutable audit logs (signer audit log is append-only) |
   447→| **RaaS com DDoS** | Ransomware-as-a-Service + DDoS is a combined extortion tactic; DDoS is infra, ransomware is endpoint | Same as above |
   448→| **Extorsão Multifacetada** | Multi-vector extortion (encrypt + leak + DDoS) | App-side: ensure audit logs cannot be deleted (append-only + hash chain from §7.3.4, pending implementation); ensure DB backups are offsite |
   449→| **Recrutamento de Insider** | Social engineering of insiders; app cannot detect intent | Audit logs (every action attributed to actor); least privilege; access revocation workflow (H8) |
   450→| **Prejuízo por Incidente** | This is an impact metric, not a vector; the app's contribution is blast-radius limiting | Risk-manager circuit breakers (5 breakers) limit financial prejuízo per incident |
   451→
   452→**The app's contribution to ransomware defense is limited to:** (a) append-only
   453→audit logs that cannot be tampered with (so the operator can verify what
   454→happened after an incident), (b) DB backups that can be restored, (c)
   455→financial circuit breakers that limit prejuízo. The actual ransomware
   456→defense (endpoint protection, EDR, immutable backups, IR plan) is
   457→operational and outside this repo.
   458→
   459→### Layer 13: APT / Espionage — OUT OF SCOPE (nation-state, operational)
   460→
   461→| Vector | Why out of scope | App-side support |
   462→|---|---|---|
   463→| **Espionagem Digital e APTs** | Advanced Persistent Threats are nation-state actors with months-long campaigns; defense requires threat hunting, network segmentation, EDR | Audit logs (detect anomalous access patterns); network isolation of signer process (already designed: signer communicates only via Unix socket) |
   464→| **Espionagem Baseada em IA** | AI-augmented espionage (automated recon, targeted phishing) — same as APT with better tooling | Same as above |
   465→| **Comprometimento de Longo Prazo** | Long-dwell attackers that establish persistence; app cannot detect | Audit log anomaly detection (future); file integrity monitoring (operational) |
   466→
   467→**The signer isolation design (Phase 1) is itself an APT mitigation:**
   468→keys live in a separate process with no network access (Unix socket
   469→only), so even if the Next.js process is compromised, the keys are not
   470→directly accessible. This is the app's strongest contribution to APT
   471→defense. Completing M2.3/M3/M4 (the signer isolation phases) is the
   472→highest-leverage APT mitigation available in app code.
   473→
   474→### Layer 14: AI-driven threats — PARTIALLY IN SCOPE
   475→
   476→| Vector | Existing mitigation | Gap | Defense |
   477→|---|---|---|---|
   478→| **Prompt Injection** | None — if `z-ai-web-dev-sdk` is used for AI features (ai-agent.ts exists) | LLM calls that take user input (scam analysis, token descriptions) are vulnerable to prompt injection | H14: input sanitization before LLM calls; output validation; separate privileged vs unprivileged LLM contexts; refuse tool-use from untrusted input |
   479→| **Shadow AI** | None | Operators using unsanctioned AI tools (external ChatGPT for trading decisions) — operational, not app-level | Out of scope. Operational policy: sanctioned AI tools only |
   480→| **Bots de Escala** | Per-IP rate limiting (partial) | Automated botnets scaling credential stuffing or API abuse | H10 (rate limiting) + H11 (DDoS) address this; no separate defense needed |
   481→| **Ataques Autônomos** | None | AI-driven autonomous attack tools (automated vulnerability scanning, automated social engineering) | Same as Layer 9 (web app hardening) — the defense doesn't change because the attacker is AI-driven |
   482→| **Phishing Hiper-realista / Deepfakes** | None | AI-generated phishing that bypasses traditional detection | Out of scope (Layer 8). Operational: security awareness; hardware keys resist phishing |
   483→
   484→**H14 acceptance criteria (if AI features are used):**
   485→- A test that asserts user input is sanitized before LLM calls (no raw user text in system prompt).
   486→- A test that asserts LLM output is validated before being used in trading decisions.
   487→- A test that asserts tool-use (function calling) is refused from untrusted input.
   488→
   489→### Layer 15: E-commerce fraud — OUT OF SCOPE (not an e-commerce platform)
   490→
   491→| Vector | Why out of scope |
   492→|---|---|
   493→| **Fraude de Triangulação** | The app is not a marketplace; no buyer-seller-mediation flow |
   494→| **Golpe da Falsa Entrega (QR Code)** | The app does not process deliveries or QR codes |
   495→| **Lojas Falsas e Ofertas Irreais** | The app is not a storefront; it trades on exchanges/DEXs |
   496→| **Phishing de Falso Suporte e Cancelamento** | Overlaps with Layer 8 Fake Support; same operational boundary |
   497→
   498→These vectors apply to e-commerce platforms. The auto-trader does not
   499→have customers, does not process orders, does not have a storefront.
   500→Including them would be scope creep into a different problem domain. If
   501→the app ever adds marketplace features (unlikely), these would become
   502→relevant — until then, they are explicitly out of scope.
