# ADR-0001 — Defense-in-Depth Architecture with Process-Isolated Signer and Fencing-Token Lease

- **Data:** 2026-07-15 (back-dated para registrar decisão arquitetural
  consolidada ao longo das fases H0 → M5).
- **Status:** Aceito. Implementado e validado. Todas as fases H0–M5
  concluídas; 0 regressões.

---

## Contexto

O projeto é um **trading engine autônomo de criptomoedas** que opera
em DEXs EVM (BSC mainnet como rede inicial; Base/Arbitrum/Optimism
propostos para M7). O operador estabeleceu como requisitos:

1. **Scam-resistance**, não "100% seguro" (requisito "irrastreável"
   descartado por incompatibilidade com AML/KYC).
2. **Audit trail completo** — toda decisão registrada em hash-chain
   append-only.
3. **Paper mode default** — live trading só via rollout controlado
   com rollback automático.
4. **100% open-source / free tier** — APIs gratuitas (Binance REST,
   DexScreener, GoPlus, alternative.me, CoinGecko, Etherscan).
5. **Defense-in-depth** — múltiplas camadas independentes; falha de
   uma camada não derruba o sistema.

O `HARDENING-ROADMAP.md` mapeia 30 attack vectors a fases. A decisão
arquitetural deste ADR é a **estrutura macro** que acomoda todas as
fases: a topologia modular, a escolha de isolamento por processo
para o signer, o uso de fencing tokens para writer lease, e a
camada de observability como fonte única de verdade para validação.

## Alternativas consideradas

### A1 — Monolito sem isolamento de processo

- Signer como módulo importado no mesmo processo que o engine de
  trading.
- **Descartada:** RCE no engine expõe a chave privada na memória
  do processo. Viola requisito de defense-in-depth.

### A2 — Worker thread em vez de processo separado

- Signer em `worker_threads` Node.js.
- **Descartada:** Worker threads compartilham heap com a thread
  principal via `SharedArrayBuffer`. Isolamento fraco. Não é
  barreira real contra RCE.

### A3 — WASM sandbox para signer

- Signer carregado como módulo WASM sandboxed.
- **Descartada:** Complexidade alta. Sem benefício de segurança
  sobre processo separado para o nosso caso de uso.

### A4 — Lock distribuído baseado em Redis sem fencing tokens

- `SET key value NX PX 30000` em Redis. Writer com lock faz
  broadcast.
- **Descartada:** Vulnerável a clock skew e GC pauses. Writer
  pode acreditar ter lock após expiry; broadcast stale causa
  double-spend ou stuck tx. Kleppmann demonstra este caso em
  "How to do distributed locking".

### A5 — Lock distribuído com fencing tokens mas sem pre-broadcast
verify

- LeaseStore emite fencing tokens, mas Broadcaster não verifica.
- **Descartada:** Fencing token sem verificação é security
  theater. O token precisa ser verificado por um serviço que
  aceita apenas tokens monotônicos para ser efetivo.

### A6 — Observability como camada final (depois de chaos/shadow/
canary/long-duration)

- Cada harness implementa sua própria coleta de métricas.
- **Descartada (DEC-004):** Causa duplicação e divergência. Cada
  harness reinventa contadores; métricas ficam inconsistentes
  entre harnesses; comparação entre runs é impossível.

### A7 — Two pipelines para shadow mode (live + shadow paralelas)

- Shadow roda pipeline própria com mesma config, compara output.
- **Descartada:** Duplica load de RPC. Divergência entre pipelines
  pode ser artefato da execução paralela, não diferença real.
  Compartilhar a MESMA Pipeline e fork do output elimina este
  ruído.

### A8 — setInterval para long-duration loop

- `setInterval(() => runtime.tick(), period)`.
- **Descartada:** setInterval não aguarda tick completar; em
  caso de tick lento, múltiplos ticks acumulam em background.
  Padrão `while (running) { await tick(); await sleep(); }`
  garante que próximo tick só começa após o anterior terminar.

## Escolha

Arquitetura **defense-in-depth em camadas**, com:

1. **Pipeline H2.6** compondo 7 gates sequenciais (liquidity →
   authority → contract → simulation → mev → approval → sell-sim).
   Cada gate é FROZEN após validação; cada gate tem REG adversarial.

2. **Signer isolado em processo próprio (M3.2)** comunicando via
   IPC serializado (`signer-protocol.ts`). Chave privada nunca sai
   do processo signer. Audit log interno com hash-chain separada.

3. **Writer lease com fencing tokens Kleppmann (M4)** emitidos
   monotonicamente. `LeasedBroadcaster` faz pre-broadcast fencing
   check: writer stale com token antigo é rejeitado mesmo que
   acredite ter a lease. REG-015/016/017/018 travam invariants.

4. **Observability como Registry único (M5.5)** consumido por
   todos os harnesses (dry-run, chaos, shadow, canary,
   long-duration) e pelo endpoint `/api/runtime/status` read-only.

5. **Shadow mode compartilhando a MESMA Pipeline (M5.2)** com
   fork de output para Live + Shadow. Incrementa `shadowDiffs`
   em divergência.

6. **Canary mode com bucketing determinístico (M5.3)**:
   `bucket = keccak256(txHash) % 100; bucket < canaryPct`.
   Permite ramp gradual de paper → live via `setCanaryPct`.

7. **ChaosInjector classes independentes (M5.4)** com interface
   `before()/after()/cleanup()`. Sem `if (chaos)` espalhado.

8. **Long-Duration loop `while (running)` (M5.6)** com sleep
   entre ticks. Suporta `--duration N` para runs de 24h/72h/7d.

## Motivação

A combinação destas escolhas forma um **sistema em camadas onde
cada falha tem defesa independente**:

- Falha de RPC poisoning → quorum H1.1 + simulation gate H1.2.
- Falha de contrato scam → contract verification H2.1 + liquidity
  H2.2 + authority H2.3 + sell-sim H2.4.
- Falha de approval ilimitado → approval hardening H1.3.
- Falha de MEV sandwich → MEV baseline H1.4.
- Falha de comprometimento do engine → signer isolado M3.2 (chave
  privada não exposta).
- Falha de split-brain de writer → fencing tokens M4 + pre-broadcast
  verify.
- Falha de classificação de erro → prefixos `BROADCAST_*` no
  Broadcaster M3.3 (corrigido em M5.4, DEC-005).
- Falha de validação operacional → Registry único M5.5 + 5
  harnesses (M5.1/M5.2/M5.3/M5.4/M5.6) cobrindo happy path,
  divergência, rollout, adversarial, e endurance.

Cada defesa é independente e testada adversarialmente (REG-NNN).
Uma defesa falhar não compromete as outras.

## Impacto

- **Complexidade:** 8 fases de hardening (H0–M5) com 30+ arquivos
  FROZEN em `src/lib/chain/` e `src/signer/`. Manutenção requer
  disciplina de não tocar FROZEN sem entrada em DECISION_LOG.

- **Latência:** Cada round atravessa 7 gates + IPC signer + lease
  acquire + broadcaster + RPC quorum. Latência P95 atual
  (validada em M5.5): pipeline ~41ms, signer ~17ms, broadcaster
  ~28ms. Total ~86ms por round. Aceitável para trading não-HFT.

- **Operação:** Runtime requer 2 processos (engine + signer) em
  hosts com comunicação IPC. Para M6 Live Trading, requer Vault/KMS
  acessível pelo signer.

- **Memória:** Long-Duration M5.6 validou 74k ops em 60s sem leak
  de heap. Estimativa: 24h = ~106M ops, crescimento de heap < 50MB.

- **Dependências:** Nenhuma adicionada nos M5 (apenas reuso de
  ethers.js, Prisma, Next.js já instalados).

## Rollback

Rollback desta arquitetura é **desproporcional ao benefício** —
envolveria remover fases H0–M5 inteiras, retroagir a monolito sem
isolamento, e perder todos os REG adversariais. **Não
recomendado.**

Se um componente específico precisar ser revertido (ex.: nova
implementação de `LeaseStore` causa regressão), rollback é
controlado via:

1. Entrada em `DECISION_LOG.md` justificando a reversão.
2. Git revert do commit específico (ou `Edit` para restaurar
   versão anterior do arquivo).
3. Rodar todos os testes M5 para confirmar 0 regressões.
4. Atualizar `PROJECT_STATE.md` e `memory/implementation-history.md`.

**Não reverter sem:** (a) causa raiz documentada, (b) teste
adversarial que pinne o bug que motivou a reversão, (c)
confirmação do operador.
