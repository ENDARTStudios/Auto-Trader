# ADR-0002 — Project OS v2.1: Manifesto, Checklist, IDs Canônicos e Snapshot Puro

- **Data:** 2026-07-16
- **Status:** Aceito. Implementado em 2026-07-16.
- **Supersedes:** nenhum (v2 → v2.1 é refinamento, não substituição).
- **Relacionado:** DEC-006 (resumo em `DECISION_LOG.md`), entrada
  em `memory/implementation-history.md` (2026-07-16).

---

## Contexto

O Project OS v2 (criado em 2026-07-15) já tinha divisão clara de
responsabilidades entre `PROJECT_STATE.md` (snapshot),
`memory/implementation-history.md` (histórico), `DECISION_LOG.md`
(decisões) e `decisions/ADR-*.md` (ADRs detalhados). Porém, três
problemas estruturais foram identificados pelo operador:

1. **`PROJECT_STATE.md` misturava snapshot com referências a
   roadmap, decisões e histórico.** Apesar de declarar "snapshot
   puro", continha seções inteiras com resumos de roadmap, lista
   de decisões ativas e referências a histórico. Isto criava
   duplicação com as fontes canônicas (`architecture/roadmap.md`,
   `DECISION_LOG.md`, `memory/implementation-history.md`) e
   abria risco de divergência.

2. **`README.md` explicava regras em vez de apenas apontar onde
   cada informação fica.** Tinha ~190 linhas com regras de
   precedência, protocolo de uso, regras adicionais — duplicando
   conteúdo de `CORE_RULES.md`, `ENGINEERING_RULES.md` e
   `INDEX.md`. Operadores e agentes perdiam tempo lendo regras
   em três lugares diferentes.

3. **Sem IDs canônicos por categoria.** Invariantes tinham IDs
   (`INV-NNN`) mas os outros documentos não. Um ADR não podia
   citar um padrão de teste sem ambiguidade ("o padrão de teste
   adversarial em ENGINEERING_RULES"). Sem IDs, cross-links eram
   frágeis (baseados em nome de arquivo, que pode mudar).

4. **Sem manifesto do Project OS.** Cada arquivo declarava suas
   próprias regras de manutenção, mas não havia um documento
   central explicando os **princípios** (fonte única de verdade,
   append-only, IDs canônicos, versionamento do próprio Project
   OS). Isto facilitava crescimento desordenado.

5. **Sem checklist obrigatório.** Apesar de `ENGINEERING_RULES.md`
   declarar o fluxo (Ler → Mapear → Planejar → Executar →
   Validar → Documentar), não havia checklist operacional
   passível de ser seguido linearmente por um agente. Agentes
   podiam pular etapas sem deixar rastro.

6. **Sem versionamento do próprio Project OS.** Mudanças
   estruturais em `.ai/` não eram versionadas explicitamente.
   Um agente lendo `PROJECT_STATE.md` não sabia qual versão da
   governança estava em vigor — apenas qual versão do projeto.

7. **Nomes de arquivos de contrato verbosos.** `contracts/api-contracts.md`,
   `contracts/database-contracts.md`, etc. O sufixo `-contracts`
   é redundante: já estão na pasta `contracts/`. Verbosidade
   adiciona ruído em cross-links.

## Alternativas consideradas

### A1 — Manter v2 sem mudanças

- **Descartada:** os 3 problemas estruturais identificados não
  se resolvem sozinhos; tendem a piorar com o tempo conforme
  novos documentos são adicionados.

### A2 — Adicionar apenas IDs e cross-links, sem MANIFEST/CHECKLIST

- **Descartada:** IDs e cross-links resolvem consistência mas
  não resolvem o problema do crescimento desordenado. Sem um
  manifesto declarando princípios, qualquer agente pode adicionar
  documentos que duplicam responsabilidade.

### A3 — Apenas consolidar README + INDEX em um único arquivo

- **Descartada:** README como índice puro (humano) e INDEX como
  índice completo com IDs (máquina + humano profundo) têm
  audiências diferentes. Consolidar forçaria um dos dois a ser
  subótimo para sua audiência.

### A4 — Versionar com SemVer (v2.1.0) em vez de v2.1

- **Descartada:** SemVer é para código com breaking changes /
  features / fixes bem definidos. Project OS é um documento de
  governança; mudanças estruturais são raras e qualitativas.
  Versionamento simples major.minor (v2.1) é suficiente e mais
  legível.

## Decisão

Adotar **Project OS v2.1** com as 7 mudanças a seguir:

1. **`MANIFEST.md` criado.** Documento central declarando:
   - Objetivo do `.ai/`.
   - 7 princípios fundamentais (fonte única, append-only,
     cross-links, IDs canônicos, snapshot vs histórico,
     precedência, versionamento do Project OS).
   - Tabela de prefixos de ID canônicos.
   - Tabela de divisão de responsabilidade (fonte canônica por
     tipo de informação).
   - Regras de manutenção.

2. **`CHECKLIST.md` criado.** Checklist operacional em 7 fases
   (Leitura → Mapeamento → Planejamento → Implementação →
   Validação → Documentação → Cross-links). Itens `[ ]` devem
   ser marcados explicitamente pelo agente antes de prosseguir.

3. **`README.md` reescrito como índice puro.** Apenas aponta
   "onde cada informação fica". Sem regras, sem protocolo, sem
   detalhes — esses ficam nos arquivos referenciados. Reduzido
   de ~190 linhas para ~70.

4. **`PROJECT_STATE.md` reescrito como snapshot puro.** Apenas:
   versão do Project OS, versão do projeto, branch, milestone
   atual, stack, banco, modo, servidor, próximo milestone, data
   de atualização, módulos FROZEN (referência a frozen-files.md),
   módulos em andamento, status M5, fluxo canônico (referência
   a runtime.md), e referências para fontes canônicas externas.
   Removidas seções de roadmap, decisões e histórico que
   duplicavam outras fontes.

5. **IDs canônicos por categoria.** Tabela de prefixos no
   `MANIFEST.md`:
   - `INV-NNN` — Invariantes (já existiam, mantidos).
   - `ADR-NNNN` — ADRs (já existiam, formalizado).
   - `DEC-NNN` — Decisões no log (já existiam, mantidos).
   - `TD-NNN` — Débitos técnicos (já existiam, mantidos).
   - `KP-NNN` — Problemas conhecidos (já existiam, mantidos).
   - `STD-NNN` — Padrões (NOVO). Numerados por bloco:
     coding=001+, testing=101+, security=201+, docs=301+,
     git=401+.
   - `REG-NNN` — Regressões de segurança (já em `SECURITY.md`,
     mantidos).
   - `FI-NNN` — Ideias futuras (NOVO prefixo formal).

6. **Cross-links obrigatórios.** Todo documento estruturado em
   `.ai/` deve ter seção `## Relacionado` no final, listando
   IDs relacionados. Regra formalizada em `INDEX.md` e
   `CHECKLIST.md` Fase 7.

7. **Versionamento do Project OS.** `PROJECT_STATE.md` agora
   declara `Project OS: v2.1` explicitamente. Toda mudança
   estrutural em `.ai/` bumpa a versão e produz novo ADR + nova
   entrada em DECISION_LOG.md + nova entrada em
   implementation-history.md.

8. **Renomeação de contracts/.** Nomes simplificados:
   - `api-contracts.md` → `api.md`
   - `database-contracts.md` → `database.md`
   - `rpc-contracts.md` → `rpc.md`
   - `event-contracts.md` → `events.md`

## Consequências

### Positivas

- **Snapshot puro:** `PROJECT_STATE.md` agora é efetivamente
  só snapshot. Manutenção fica trivial: atualizar campos
  superficiais quando estado muda. Não há risco de divergência
  com roadmap/decisões/histórico.

- **README mínimo:** operador ou agente novo lê ~70 linhas e
  sabe onde está cada informação. Antes eram ~190 linhas
  misturando índice com regras.

- **IDs canônicos:** qualquer documento pode citar outro sem
  ambiguidade. Ex.: "viola STD-005 (preservar cause)" é mais
  preciso que "viola o padrão de error handling". Permite
  navegação por referência cruzada.

- **Cross-links:** descoberta de documentos relacionados é
  automática. Um agente lendo `INV-007` encontra links diretos
  para `STD-205`, `DEC-003`, `REG-015`, `ADR-0001`. Reduz
  tempo de descoberta de contexto.

- **Manifesto:** princípios do Project OS agora estão em um
  único local. Mudanças estruturais futuras têm referência
  clara do que estão preservando ou alterando.

- **Checklist operacional:** agentes podem seguir linearmente
  as 7 fases. Reduz chance de pular leitura de contexto
  (causa #1 de regressões).

- **Versionamento:** agentes futuros saberão que v2.1 inclui
  MANIFEST/CHECKLIST/IDs; v2 não. Permite que um agente
  detecte se está operando contra versão obsoleta da governança.

### Negativas

- **Mais arquivos para manter:** MANIFEST.md e CHECKLIST.md
  adicionam 2 arquivos à raiz. Porém, são arquivos de
  referência (lidos mas raramente editados) — custo baixo.

- **Risco de cross-link desatualizado:** se um documento é
  renomeado, cross-links podem quebrar. Mitigação: regra
  formal em MANIFEST.md de que renomeação é mudança
  estrutural (exige ADR).

- **Curva de aprendizado de IDs:** agentes e operadores novos
  precisam aprender os prefixos. Mitigação: tabela no
  MANIFEST.md e referência rápida no INDEX.md.

### Neutras

- **Renomeação de contracts/`: quebra links externos (se houver)
  para `api-contracts.md`. Porém, v2 foi criado em 2026-07-15
  (1 dia antes); nenhuma referência externa consolidada ainda
  existe. Custo baixo.

## Rollback

Rollback para v2 é **desproporcional ao benefício** — envolveria:

1. Remover MANIFEST.md e CHECKLIST.md.
2. Restaurar README.md v2 (~190 linhas com regras).
3. Restaurar PROJECT_STATE.md v2 (com seções de roadmap/decisões).
4. Remover IDs STD-NNN dos 5 arquivos de standards/.
5. Remover seções `## Relacionado` de todos os arquivos.
6. Renomear contracts/ de volta para `*-contracts.md`.
7. Atualizar INDEX.md para remover referências a MANIFEST/CHECKLIST.
8. Atualizar PROJECT_STATE.md para reverter versão.
9. Criar ADR-0003 justificando a reversão.

**Não recomendado.** Se problemas surgirem com v2.1, preferir
refinamentos incrementais (v2.2, v2.3) sobre reversão para v2.
