# ADR-0003 — Project OS v2.2: Rastreabilidade Completa, MOD-IDs e STATE Markers

> **STATE: APPEND-ONLY** — ADR — supersedure via novo ADR, nunca editado.

- **Data:** 2026-07-16
- **Status:** Aceito. Implementado em 2026-07-16.
- **Supersedes:** nenhum (v2.1 → v2.2 é refinamento, não substituição).
- **Relacionado:** DEC-007 (resumo em `DECISION_LOG.md`), entrada
  em `memory/implementation-history.md` (2026-07-16), ADR-0002
  (transição v2 → v2.1 que este ADR estende).

---

## Contexto

O Project OS v2.1 (introduzido em ADR-0002) estabeleceu os
fundamentos da governança: manifesto, checklist, IDs canônicos
por categoria (INV/ADR/DEC/TD/KP/STD/REG/FI), regra de cross-links,
versionamento do Project OS, e `PROJECT_STATE.md` como snapshot
puro. Esta estrutura resolveu problemas de duplicação e
crescimento desordenado.

Porém, após uso operacional por um ciclo, o operador identificou
**sete lacunas de rastreabilidade** que v2.1 não endereça:

1. **`CORE_RULES.md` crescia continuamente.** Regra 11 ("todo bug
   deve produzir aprendizado") foi adicionada como regra absoluta,
   mas é na verdade uma regra **operacional** — pode ser refinada
   (novos formatos de post-mortem, novas ferramentas de tracking)
   sem que o princípio fundamental mude. Misturar regras permanentes
   com operacionais abre caminho para `CORE_RULES.md` crescer
   indefinidamente e perder imutabilidade.

2. **Módulos não tinham IDs padronizados.** ADRs, DEC, INV, TD, KP,
   STD e REG tinham prefixos canônicos, mas módulos eram
   referenciados por nome de arquivo ou fase do roadmap
   (ex.: "Pipeline (H2.6)"). Isto dificultava cross-links em ADRs
   e worklogs — "qual módulo exatamente?" era ambíguo em cenários
   com múltiplos arquivos por fase.

3. **Sem matriz de rastreabilidade.** Apesar de cada invariante
   (INV-NNN) ter ADR associado, módulo implementador, REG-NNN
   que o defende e script de teste que o valida, estes quatro
   elementos estavam espalhados por 5+ arquivos. Não havia
   matriz única que respondesse "qual teste garante este
   invariante?" sem auditoria manual.

4. **Testes espalhados sem catálogo.** Scripts em `scripts/test-*.ts`
   eram 24 arquivos, mas não havia índice dizendo "para mudar o
   Broadcaster, rode estes 3 testes". Cada investigação começava
   do zero.

5. **Documentação sem estado explícito.** Apenas código tinha
   marcador FROZEN. Documentação crítica (ex.: `architecture/runtime.md`
   que define o fluxo canônico) podia ser editada sem sinal de
   que era imutável. Estado implícito é estado quebrado.

6. **Sem diagrama de árvore de dependências.** Embora
   `architecture/dependencies.md` descrevesse relações em texto
   e tabela, faltava um único diagrama ASCII mostrando o fluxo
   top-level (Pipeline → SignerAdapter → Signer RPC → Writer Lease
   → Broadcaster → RPC Quorum → Blockchain). Tabela é ambígua
   para topologia; diagrama elimina ambiguidade.

7. **IDs espalhados sem catálogo consolidado.** Saber "quais
   ADRs existem?" exigia `ls .ai/decisions/`. Saber "quais REG-NNN
   defendem INV-007?" exigia grep em SECURITY.md + invariants.md.
   Sem catálogo único, colisão de IDs era risco futuro.

---

## Decisão

Bumpar o Project OS de **v2.1 para v2.2** com sete mudanças
estruturais que fecham as lacunas identificadas:

### 1. Separar regras permanentes de operacionais em `CORE_RULES.md`

- `CORE_RULES.md` agora contém **apenas 10 regras permanentes**
  (leis fundadoras que não mudam com fase, stack ou framework).
- Adicionado "Princípio de separação" no topo declarando o critério:
  regra entra em `CORE_RULES.md` só se for verdadeira em qualquer
  fase do projeto.
- Regra 11 ("todo bug deve produzir aprendizado") **movida** para
  `ENGINEERING_RULES.md > Cultura de aprendizado (pós-bug)` como
  seção operacional, com nota explícita de que pode ser refinada.
- `CORE_RULES.md` marcado `STATE: FROZEN` (imutável por princípio).
- `ENGINEERING_RULES.md` marcado `STATE: ACTIVE` (evolui com o processo).

### 2. Introduzir MOD-IDs canônicos para módulos

- Todo módulo do projeto recebe MOD-ID permanente derivado da fase:
  - `MOD-H*` — hardening fundacional (audit, RPC, gates).
  - `MOD-M3.*` — sub-fases M3 (signer isolation).
  - `MOD-M4.*` — sub-fases M4 (writer lease).
  - `MOD-M5.*` — sub-fases M5 (runtime harnesses + observability).
  - `MOD-M6`+ — milestones futuros (placeholders).
  - `MOD-TR-*` — camada de trading (não-hardening).
  - `MOD-API-*` — endpoints da API Next.js.
  - `MOD-UI-*` — componentes do dashboard.
- IDs são **permanentes** — não reusados nem renomeados.
- `architecture/modules.md` atualizado com coluna MOD-ID em todas
  as tabelas.

### 3. Criar `.ai/TRACEABILITY.md` — matriz de rastreabilidade

- Matriz principal liga cada `INV-NNN` a `ADR-NNNN`, `MOD-NNN`,
  `REG-NNN` e script de teste.
- Tabela inversa liga cada `REG-NNN` ao `INV-NNN` que defende.
- Cobertura por módulo mostra quais MOD-IDs têm defesa adversarial.
- Seção "Pendências" lista lacunas (INV sem REG) como TD-NNN
  propostos.
- Seção "Como usar" documenta 3 cenários canônicos (mudança de
  módulo, criação de invariante, teste falhando).

### 4. Criar `.ai/tests.md` — catálogo de testes

- Indexa todos os 24 scripts `scripts/test-*.ts` por milestone
  (H0, H1, H2, M3, M4, M5).
- Para cada teste: script, contagem de asserts, linhas, cobertura
  (MOD-ID + INV-NNN + REG-NNN), responsável histórico.
- Tabela consolidada mostra total por milestone (24 scripts,
  1.487 asserts, 15.759 linhas).
- Tabela de cobertura por invariante mostra quais INV têm teste
  direto.
- Seção "Pendências" lista testes faltantes (REG-019/020/021/022/023
  propostos).
- Comandos para rodar testes individuais, por milestone, e suite
  completa.

### 5. Adicionar STATE markers a todos os arquivos de governança

- Vocabulário: `FROZEN`, `ACTIVE`, `DRAFT`, `APPEND-ONLY`, `SNAPSHOT`.
- Script `scripts/add-state-markers.py` (persistido) aplicou
  markers a 33 arquivos (4 já tinham markers; 37 total).
- Distribuição:
  - `FROZEN` (imutável): CORE_RULES, PROMPTING_RULES, OUTPUT_RULES,
    MANIFEST, architecture/runtime, architecture/invariants,
    contracts/*, context/project-summary.
  - `ACTIVE` (evolui): ENGINEERING_RULES, README, INDEX, CHECKLIST,
    TASK_TEMPLATE, architecture/modules, architecture/interfaces,
    architecture/dependencies, architecture/frozen-files,
    architecture/roadmap, standards/*, context/terminology,
    context/conventions, context/glossary.
  - `SNAPSHOT` (reescrito): PROJECT_STATE.
  - `APPEND-ONLY` (entrada adicionada, nunca removida):
    DECISION_LOG, memory/*, decisions/ADR-*.

### 6. Adicionar diagrama de árvore canônica de dependências

- `architecture/dependencies.md` agora abre com diagrama ASCII
  top-level mostrando o fluxo: Market Data → Pipeline →
  SignerAdapter → Signer RPC → WriterLease → LeasedBroadcaster →
  Broadcaster → RPC Quorum → Blockchain → Audit Log.
- Cada nó do diagrama tem MOD-ID e estado FROZEN marcado.
- Resumo linear abaixo do diagrama para leitura rápida.
- Diagrama é declarado como "única topologia aceita" — desvio
  viola INV-001 e requer ADR.

### 7. Criar `.ai/IDS.md` — catálogo consolidado de IDs

- Lista todos os IDs emitidos em 9 categorias: ADR, DEC, INV, MOD,
  REG, STD, TD, KP, FI.
- Para cada ID: título, arquivo-fonte canônico, status.
- Tabelas separadas por prefixo para navegação rápida.
- Regras de manutenção: adicionar entrada ao criar novo ID,
  nunca remover (permanência), numeração sequencial por bloco.

## Alternativas descartadas

- **Manter v2.1 sem mudanças** — descartado: lacunas de
  rastreabilidade são críticas para M6 (live trading). Sem
  matriz INV→REG→teste, não há como provar que o sistema
  defende o que afirma defender antes de arriscar capital real.

- **Apenas IDS.md + TRACEABILITY.md, sem MOD-IDs** — descartado:
  TRACEABILITY sem MOD-IDs seria ambígua ("qual módulo exatamente
  implementa INV-002?"). MOD-IDs são pré-requisito da matriz.

- **Apenas MOD-IDs, sem STATE markers** — descartado: MOD-IDs
  resolvem rastreabilidade mas não resolvem o problema de
  documentação crítica sendo editada sem sinal. STATE markers
  são complementares.

- **Substituir `CORE_RULES.md` por dois arquivos
  (`PERMANENT_RULES.md` + `OPERATIONAL_RULES.md`)** — descartado:
  fragmentação adicional sem benefício. Melhor manter
  `CORE_RULES.md` como permanente e direcionar regras operacionais
  para `ENGINEERING_RULES.md` (que já existe).

- **SemVer (v2.2.0) em vez de v2.2** — descartado (mesma decisão
  que ADR-0002): SemVer é para código; Project OS é governança
  qualitativa.

- **Diagrama de árvore como Mermaid em vez de ASCII** — descartado:
  ASCII é legível em qualquer editor, terminal ou diff. Mermaid
  requer renderização. Para documento de referência canônico,
  ASCII é mais resiliente.

## Consequências

### Positivas

- **Rastreabilidade completa.** Para cada invariante, é possível
  seguir a cadeia INV → ADR → MOD → REG → teste em segundos
  consultando `TRACEABILITY.md`. Antes, isto exigia auditoria
  manual de 5+ arquivos.

- **Imutabilidade declarada.** `CORE_RULES.md` marcado FROZEN
  impede crescimento desordenado. Toda nova regra operacional
  vai para `ENGINEERING_RULES.md` por padrão. Para adicionar
  regra permanente, ADR é obrigatório.

- **Navegação por ID.** MOD-IDs permitem referência sem
  ambiguidade em ADRs, worklogs e SECURITY.md. "MOD-M3.3" é
  único; "Broadcaster (M3.3)" é ambíguo ( Broadcaster é nome
  comum).

- **Catálogo único de IDs.** `IDS.md` responde "quais ADRs
  existem?" sem `ls`. Detecta colisão futura de IDs. É a fonte
  para verificação automática (futuro script `verify-ids.py`).

- **Testes indexados.** `tests.md` responde "quais testes
  cobrem o Broadcaster?" instantaneamente. Reduz tempo de
  investigação de regressão.

- **Diagrama canônico.** Desenho ASCII da árvore de
  dependências elimina ambiguidade textual. Quando em dúvida
  sobre "quem chama quem", consulte o diagrama.

- **Estado explícito.** STATE markers transformam "deveria
  estar FROZEN" em "está FROZEN". Edição acidental de
  `architecture/runtime.md` agora é violação visível.

### Negativas

- **Mais arquivos para manter.** 37 → 40 arquivos (3 novos:
  IDS, TRACEABILITY, tests). Cada novo INV/ADR/MOD/REG exige
  atualização em 2-3 arquivos (definição + IDS + TRACEABILITY).
  **Mitigação:** script `verify-ids.py` (a criar) detecta
  inconsistências.

- **Risco de desatualização da matriz.** Se `TRACEABILITY.md`
  não for atualizada junto com novos REG-NNN, a matriz fica
  desatualizada e perde valor. **Mitigação:** item obrigatório
  no `CHECKLIST.md` (a atualizar em follow-up).

- **Overhead de leitura.** Sequência obrigatória agora tem 14
  passos (antes 12). Para mudanças triviais (typo fix), pode
  parecer excessivo. **Mitigação:** mudanças triviais não
  precisam de todos os passos — `CHECKLIST.md` deve escalar
  por risco (a refinar).

## Rollback

Esta mudança é backwards-compatible. Para reverter:

1. Remover os 3 novos arquivos (`IDS.md`, `TRACEABILITY.md`,
   `tests.md`).
2. Restaurar Regra 11 em `CORE_RULES.md` (git revert deste ADR).
3. Remover coluna MOD-ID das tabelas em `architecture/modules.md`.
4. Remover diagrama de árvore do topo de `architecture/dependencies.md`.
5. Bumpar `PROJECT_STATE.md` de volta para v2.1.
6. Atualizar `INDEX.md` e `README.md` para remover referências.
7. Adicionar DEC-008 registrando a reversão.

STATE markers podem permanecer (são aditivos e não quebram nada).

## Lição permanente

Toda camada de governança precisa de **rastreabilidade completa**
entre seus elementos. IDs canônicos por categoria (v2.1) resolvem
consistência de referência, mas não resolvem rastreabilidade —
é possível ter IDs consistentes sem matriz que mostre como eles
se relacionam. Rastreabilidade é o que permite responder "qual
teste garante este invariante?" sem auditoria manual.

Os 5 elementos da rastreabilidade — INV, ADR, MOD, REG, teste —
formam uma cadeia. Quebrar qualquer elo (INV sem REG, REG sem
teste, teste sem MOD, MOD sem ADR, ADR sem INV) é pendência
técnica. A matriz em `TRACEABILITY.md` torna estes elos visíveis.

Formalizado em:
- `MANIFEST.md` (princípios do Project OS).
- `TRACEABILITY.md` (matriz canônica).
- `IDS.md` (catálogo de IDs).
- `tests.md` (catálogo de testes).
- `architecture/modules.md` (MOD-IDs).
- `architecture/dependencies.md` (diagrama canônico).
